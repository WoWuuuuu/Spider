## 一、已确认的剩余事项（拓扑图「没整完」的部分）

### 1.1 🐛 ② 规则卡标题截断 —— 设计规格被违反 · ✅ **已修（见 §0）**

**现象**：真机截图里规则卡标题被截成 `Block…`、`Domai…`（5~6 个字母就触发省略号）。

**根因**：`TopologyLayout.placeArc` 把可变宽度槽位的上限硬锁在 **62 原型单位**（`coerceIn(34f, 62f)`）。换算到 480px 宽屏幕 ≈ **81px**。`drawCard` 里 `maxW = box.w * 0.8` → 可用文字宽度仅 **65px**；而字号下限是 **10.5dp**（density 2 时 21px），"Block" 粗体占约 57~63px，刚好越界。

矛盾点：
- 当规则只有 2 张时，弧形区总宽 342 单位，均分可达 168 单位 → 但硬锁 62，大量空间浪费。
- 计划 §1.2 明确写「**规则名（整行，不截断优先）**」。

**建议修法**：
1. **首选**：把 `placeArc` 的 flex 上限从常量 62 改成「以当前这批规则里最长标题所需的宽度为下限」，同时不超过可用均分空间。即：
   ```
   flexW = ((w - gap_total - fixed) / flex)
       .coerceAtLeast(34f * unit.x)
       .coerceAtMost(max(62f * unit.x, longestTitleWidth + pad*2))
   ```
   这样卡片在规则少时自动放宽，规则多时回退到 62。
2. **备选**：在 `drawCard` 里做字号自适应（先按 10.5dp 量，若超限则缩到 8dp  floor），保持槽位美观但牺牲一点字号。

**工作量**：~20 行（`TopologyLayout.kt` + `TopologyView.kt`），需重跑布局验证脚本。

### 1.2 ⚠️ 分组胶囊目前是「纯装饰」—— 切换分组不改变拓扑图 · ✅ **已修（见 §0）**

**现象**：点分组胶囊换到另一个组，拓扑图没有任何变化，只有胶囊文字变了。

**根因**：`TopologyModel.load()` 读取的是全局数据：
- 规则：`rulesDao.allRules()`（全库启用的规则）
- 节点：`proxyDao.getAll()`（全库所有节点）

内核本身也是全库取节点（`ConfigBuilder.kt:126-130`），所以**不显示 ≠ 内核不运行**。但这对用户来说：分组下拉成了一个「摆设」。

**关联**：这与下面的「出站切换能否只切当前分组」是同一颗树根。

### 1.3 ❌ 「工具栏缺重组和搜索」—— **我写错了，撤销这一项**（2026-09-16 更正）

**原判断**：计划 §2 的手势表写着「工具区 = 重组 / 搜索 / 设置」，而实现只有电源 + 设置，所以判为漏做。

**复核原型 v6 后推翻**：

| 项 | 原型里的真实位置 | 结论 |
|---|---|---|
| 顶栏工具区 | `spider-ui-prototype-v6.html:447-450`，`.tools` 里**只有** `⏻` 和 `⚙` | App 的**实现是对的**，一个都不缺 |
| 「重新排布」 | `:506`，在 `.debugbar` 里，与「浅色 / 深色 / 切换密度 / 重置」并列 | **原型专用的调试控件**，不是产品功能 |
| 搜索 | `:1215`，`.pop-search`，在**节点选择弹窗内部**，且仅当节点数 > 6 才出现 | 属于弹窗，不属于顶栏 |

也就是说：计划 §2 那一行把「原型调试栏里的东西」当成了「产品设计」。**不要往顶栏加这两个按钮。**

**顺带算了一下顶栏宽度预算**（为什么加了会出事）：

```
窄屏 360dp：padding 8 + 胶囊上限 228 + 按钮 44×2 = 324dp  ✓ 还剩 36dp
再加 2 个按钮：8 + 228 + 44×4 = 412dp                  ✗ 超 52dp，胶囊会被挤出屏幕
```

**原型里真正对应「搜索」的东西**是节点选择弹窗，而且它比 App 现在的强：

- 搜索框（按**节点名**或**协议**过滤，`:1193-1194`）
- 三种排序：按延迟 / 按名称 / 按协议（`:1189-1190`）
- 每行显示 `协议 · 所属分组`（`:1203`，即 `grpOf(k)`）

⚠ 注意：这个弹窗列出的是**全部分组的节点**（每行还标着所属分组），
**原型自己也没有把选择器限制在当前分组** —— 这一点和我 §2 的调研结论一致。

**所以真正的可选项不是「加按钮」，而是「要不要在新 UI 里做一个原型那样的节点选择弹窗」**
（带搜索 + 排序 + 分组标签），替代现在直接跳 `ProfileSelectActivity` 的做法。
这是**新功能**，不是补漏，需要你单独决定要不要做。

### 1.4 📊 ① 层流量是「累计值」而非「实时速率」

计划 §1.2 要求 chip 副信息显示「↑上行 / ↓下行 **实时速率** + 命中规则名」。
- 当前 `/connections` 只给 `upload` / `download` 的**累计总量**。
- 阶段 3 已知取舍：「单次下拉只能显示累计量；实时速率需要两次采样」。
- 详情浮层底部已诚实标注：「Traffic is the cumulative total... not a live rate.」

**建议**：不做持续轮询（D1 能耗决定），但在**下拉刷新**时对比上一次 snapshot 的累计值，计算「本次刷新间隔内的速率」并显示在 chip 副信息里。这样只有手动刷新时才有速率，不需要常驻轮询。

**工作量**：~30 行（snapshot 缓存上一次值 + 差值 / 时间间隔）。

## 二、核心问题：路由规则 & 出站节点能不能只切「当前分组」的节点？

### 2.1 现状

| 维度 | 当前行为 |
|---|---|
| ③ 层节点池 | `proxyDao.getAll()` → **全库所有节点**（截图显示 42 nodes total） |
| ② 层规则池 | `rulesDao.allRules()` → **全库启用的规则**，与分组无关 |
| 长按规则换出口 | `ProfileSelectActivity` → `ConfigurationFragment(select=true)` → ViewPager2 展示**所有分组**的 tab，可跨组选节点 |
| 分组胶囊 | 仅改 `DataStore.selectedGroup` 和标签文字，不影响拓扑图数据 |

### 2.2 技术上能不能限制？

**能，有三种实现路径**：

| 方案 | 做法 | 工作量 | 风险 |
|---|---|---|---|
| A. 改 `ConfigurationFragment` 加 `lockGroupId` | 构造器新增参数，在 `reload()` 里过滤 `newGroupList` | ~5 行 | **副作用陷阱**：`reload()` `:991-995` 在 `groupList.size == 1` 时会写 `DataStore.selectedGroup`。锁到单组后总是 1 → 打开 picker 会**静默切换旧 UI 的当前分组**。必须加 `if (!select)` 保护。 |
| B. 新建轻量 Picker Activity | 自己写 RecyclerView + `proxyDao.getByGroup(gid)`，返回 `EXTRA_PROFILE_ID` | ~150 行 | 零风险，但需自行实现行渲染（旗帜、延迟、选中态）。 |
| C. 保持全组但默认切到当前组 tab | `ProfileSelectActivity` 已传 `selectedItem?.groupId ?: DataStore.currentGroupId()`，**默认已经在当前组 tab**。 | 已如此 | 无风险，零改动。 |

### 2.3 限制后的语义陷阱（这才是关键）

**规则不是分组作用域的。** `RuleEntity.outbound` 存的是 profile ID，内核在 `ConfigBuilder.kt:126-130` 按 `outbound` 全库 `getEntities()` 取节点，**没有任何 group 过滤**。这意味着：

1. **合法但跨组的规则会「修不了」**：某条规则指向 group B 的节点，而用户当前在 group A。若 picker 只显示 A 的节点，这条规则的出口在界面上就变成「不可触碰」。
2. **③ 层会展示「不可选」的节点**：图上有一张 group B 的出站卡，但 picker 里找不到它 —— 用户困惑。
3. **旧 UI 一直允许跨组**：`RouteSettingsActivity` 的 `selectProfileForAdd` 没有 group 限制。

> 计划 §3 阶段 4 已记录过这个决策：「`RuleEntity.outbound` 可以指向任意分组的节点 —— 限制成单组反而**减少**能力」。

### 2.4 推荐做法（三档，由你选）· ✅ **用户选了 L2 并已实施（见 §0）**

| 档位 | 行为 | 影响 |
|---|---|---|
| **L1（推荐）** | 维持现状：picker 开放所有分组，**默认 tab 已在当前分组**（已通过 `selectedItem?.groupId` 实现）。分组胶囊保持 cosmetic，但加一行说明「拓扑图显示全局规则与节点」。 | 零代码改动，能力不丢失。 |
| **L2** | 拓扑图和 picker **默认全局**，但 picker 里加一个「☑ 仅当前分组」开关；分组胶囊切换时，拓扑图的 **③ 层过滤为当前分组节点**（`getByGroup`），② 层保持全局（规则本身无分组）。 | 中等工作量：改 `TopologyModel.load(groupId?)` + picker UI。用户可随时切回全局。 |
| **L3（强锁）** | 拓扑图、picker、节点池全部硬锁到当前分组。跨组节点在图上不可见、在 picker 里不可选。 | 工作量最大；且必须接受「跨组规则在新 UI 下不可维护」这一能力损失。若某规则指向了别的组的节点，它在新 UI 里会变成「孤儿 / 错误」态。 |

**我的建议**：选 **L1** 或 **L2**。L3 会让新 UI 的能力**严格小于**旧 UI，违反「不得影响现有功能」的红线（除非用户明确接受）。

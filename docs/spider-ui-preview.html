Spider 新 UI · 三层拓扑预览

几何 / 配色 / 连线全部由 App 里的真算法生成，不是手画的示意图。

这张图忠实到什么程度

忠实：三层的落点（真 placeScattered / placeArc）、 景深缩放与透明度、连线控制点（真 TopologyEdges.route）、 每段的笔宽与透明度、全部颜色（真 TopologyColors）。

不忠实：文字截断用的是估算字宽（真机是 TextUtils.ellipsize 的真实测量）， 字体也交给浏览器。所以别拿它判断「某个标题会不会被截断」，只看布局、配色、连线与整体观感。

背景色是预览假定值 —— 视图本身透明，真机上透出的是 App 主题背景。

① → ② 的线为什么这么多

实测约 79% 的 ①→② 曲线会从别的 chip 后面穿过（②→③ 只有 0.7%）。 这不是 bug：原型的 drawLines() 对 kind==='in' 的边完全不做避障， 而且 ①→② 用 opacity=".42"、②→③ 用 .85； svg.lines 是 z-index:3 而卡片是 4~7 —— 线本来就在卡片底下，chip 又是半透明玻璃，穿过去正是那层质感的一部分。

本项目还顺带修掉一处走样：drawEdges 原先对所有边一律 stroke-width 1.2 / alpha 217，等于把 ①→② 也画成实色， 在 79% 的穿透率下会糊成一层密网。现已按段分开。

① 层的容量是量出来的，不是拍的

① 区能放几张 chip，限制**不是面积**，而是每行放得下几张： chip 宽度上限 120 个原型单位 × 1.15 景深预留 = 138 单位，而 ① 区宽只有 342 单位 —— 最宽的标签每行只放得下 2 张。26 张就要 13 行，而这块高度只排得下约 11 行。

验证结果（4 种屏幕 × 16 颗种子，按绘制矩形判）： 混合宽度标签第 24 张起放不下；全宽标签（最坏情况）第 23 张起放不下。 所以上限取 IN_MAX = 22，超出的折进「+N 更多」胶囊。

提上限时还顺手修掉一个一直存在的隐患：布局按 chipWidth×1.15 预留宽， 但高只按 22 预留，而绘制时宽高都乘景深缩放 —— 画出来的 chip 比预留的框高。 18 张时行数少、余量足，刚好蒙过去；提到 26 张就暴露成 128 处越界。 现在高也按 ×1.15 预留、绘制时再除回来，于是「预留框 ⊇ 任何画出来的矩形」在构造上成立。

阶段 4：能点的东西

单击 ① chip → 底部详情浮层（host / 地址 / 进程 / 上下行 / 命中规则 / 建立时间）。 浮层是同一棵视图树里的一层，不是 Dialog 也不是新 Fragment —— 否则会走一遍生命周期， 下拉刷新拿到的实时连接就没了。

单击 ② 规则卡 → 规则编辑页；单击 ③ 出站卡 → 节点编辑页； 单击「+N 更多」→ 完整列表。

长按 ② 规则卡 → 快速换出口节点（全计划唯一一条写操作，走 ProfileManager.updateRule + needReload()，让用户确认后再重载）。
长按 ① chip → 复制 host:port。

③ 层的「直连 / 拦截」不是可编辑实体，点了不做任何事 —— 它们表达的是「动作」， 没有对应的设置页可开。

另外 ① 层现在的上行/下行是 /connections 的累计值而非速率； 浮层里也明确写了这一点。要显示实时速率需要两次采样或轮询，那是暂缓的能耗决定。
